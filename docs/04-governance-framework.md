# 04. Governance Framework

Independent portfolio/research project — no institutional governance body actually exists for this prototype. Roles below describe what a real pilot *would* need, and are marked PROPOSED DESIGN throughout, not an active governance structure.

## Governance objectives

1. No result generated by this project is ever presented as stronger evidence than it is (DOCUMENTED vs EXPECTED vs OBSERVED vs VERIFIED, per the provenance register).
2. No personal farmer data is ever required or collected by this prototype.
3. No output reaches a hypothetical end user without an uncertainty estimate and a human-review flag.
4. Synthetic and real data are never mixed or confusable (see `data/README.md`).

## Data inventory (what this prototype actually touches)

| Data element | Status | Sensitivity |
|---|---|---|
| Synthetic demonstration data (`data/processed/synthetic_demo/`) | Generated locally, no external source | None — not real |
| Real agricultural records (`sajidahmed12` jute/wheat CSVs, fetched via `scripts/fetch_real_data.py`) | OBSERVED schema and adapter; source lineage and units unresolved | Aggregate crop/area/production/rainfall records; no individual-level fields were observed in the inspected schema. Do not describe them as officially verified statistics. |
| Any future field-collected farmer data | **Not implemented, not collected, not planned for this prototype** | Would be Confidential/Sensitive if ever added — out of scope here |

## Data classification

Using the same Public/Internal/Confidential/Sensitive scheme as the companion `rai-govtoolkit-bd` project:

| Element | Classification | Handling |
|---|---|---|
| Synthetic demo data | Public | Freely shareable — it's fake |
| Jute/wheat district-name/crop/year aggregates from the third-party GitHub source | Research data; provenance/rights unresolved | Raw CSVs are excluded from this release. Retrieval is checksum-verified; source lineage and dataset-specific rights must not be overstated. Other sources remain subject to their actual licences. |
| Any individual farmer-level data | Would be Sensitive | **Not used anywhere in this prototype** |

## Access control

This is a public, open-source repository. There is no access-control system because there is no sensitive data to protect in its current form. If real farmer-level data were ever added (not currently planned), this section would need a complete rewrite before that happened, not after.

## Retention

Synthetic data: retained indefinitely (it's a test fixture). Real data fetched via `scripts/fetch_real_data.py`: subject to the retention/redistribution terms of its original source licence, which must be confirmed (several are currently LICENSE REQUIRES REVIEW) before any real data is committed to this repository or redistributed further.

## Data quality

Enforced in code, not just described: `src/data/validation.py` checks missingness, duplicates, and physically-implausible values (e.g. negative rainfall) before any data reaches modelling. See `outputs/reports/run_log.md` for the actual validation report from the most recent pipeline run.

## Privacy

- No personal data fields are used anywhere in this prototype's schema.
- `src/governance/checks.py::check_no_personal_data()` runs an automated check against a forbidden-field list (name, phone, NID, address, etc.) on every pipeline run — if a future contributor accidentally adds such a field, the check fails loudly rather than silently passing.

## Security

See `SECURITY.md`. No API keys or credentials are committed to this repository; `scripts/fetch_real_data.py` expects the user's own Kaggle credentials to be configured locally, never hardcoded.

## Bias and representation

- **Risk:** district/crop coverage in any real dataset may be uneven (some regions or crop types overrepresented).
- **Mitigation in code:** `src/governance/checks.py::check_district_coverage()` flags datasets covering too few districts to say anything about geographic variation. This is a minimum-viable check, not proof of balanced representation — it catches the single-region failure mode, nothing subtler.
- **Known limitation:** no check currently exists for crop-type balance or socioeconomic representation (e.g. smallholder vs. large-farm data sources) — flagged as a gap, not silently assumed to be fine.

## Explainability

`src/models/explain.py` reports Random Forest feature importances and Ridge coefficients — explicitly labelled with the caveat that impurity-based importance is biased toward high-cardinality features (a documented scikit-learn limitation, stated in the module's own docstring rather than hidden).

## Uncertainty

Every model evaluation reports MAE and RMSE together as aggregate error metrics (`src/governance/checks.py::check_error_metrics_present()` enforces this), **and separately** a real split-conformal prediction interval with its own empirically-measured coverage (`check_prediction_interval_present()`). These were previously conflated — an earlier version described MAE/RMSE itself as an "uncertainty range," which pre-release review correctly identified as a technically incorrect characterization of an aggregate metric. The decision-support output contract (`src/product/schemas.py`) now reports both separately: `evaluation_error_context` (MAE/RMSE) and `prediction_interval` (the actual conformal bound).

## Human oversight

`src/product/schemas.py::build_recommendation()` hardcodes `recommended_action_type = "human_review"` — there is no code path in this repository that produces an output without that flag. This is the single most important governance control in the codebase: the model's output literally cannot present itself as a final instruction, by construction.

## Incident response (PROPOSED DESIGN)

No live system exists to have an incident. If this ever becomes a real pilot: a data-quality or model-performance anomaly would need a named owner, a rollback-to-baseline procedure, and a disclosure process to any downstream users — none of which exists today because none is needed today.

## Model change management

Every pipeline run is tagged with a `model_version` string (`sonardesh-ai-v0.1` currently) in the decision-support output contract. A real pilot would need semantic versioning tied to retraining events and a documented approval step before a new version replaces an old one in front of any user — not implemented, since there is no user-facing deployment.

## Auditability

- `outputs/reports/experiment-registry.csv` — append-only log of every pipeline run's actual metrics, written by code, never hand-edited.
- `outputs/reports/run_log.md` — full human-readable log of the most recent run, including validation results, cleaning report, model comparison, and governance-check results.
- `docs/research/source-audit.md` — this project's own self-audit of its documentation for unsupported claims (see that file for findings).

## Monitoring (PROPOSED DESIGN for a real pilot — not implemented here)

A real deployment would need: data freshness monitoring, model-performance drift tracking against new real-world outcomes, and equity-disaggregated performance tracking by district. None of this is implemented in this prototype because there is no live deployment to monitor.

## Escalation

Not applicable to a static repository. In a real pilot, this would route to the (currently unfilled) data steward and domain reviewer roles above.
